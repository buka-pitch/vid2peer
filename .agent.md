# Build a Decentralized P2P Video Chat Application

You are a senior distributed-systems and networking engineer. Build a production-oriented prototype of a **peer-to-peer video/audio calling application** that works between:

- Web browsers
- Android devices

The application should prioritize **true peer-to-peer media communication**, decentralized peer discovery, privacy, and a clean modular architecture.

## 1. Core Architecture

Use this architecture:

```text
                 ┌──────────────────────┐
                 │   Bootstrap / Relay   │
                 │       Peers           │
                 └──────────┬───────────┘
                            │
                     Discovery / Relay
                            │
             ┌──────────────┴──────────────┐
             │                             │
      ┌──────▼──────┐               ┌──────▼──────┐
      │   Browser   │◄────WebRTC────►│   Android   │
      │   Peer A    │               │   Peer B    │
      └──────┬──────┘               └──────┬──────┘
             │                             │
             └────────── libp2p ───────────┘
                    signaling /
                    discovery
```

Important:

**Do NOT build a centralized media server.**

The video and audio streams should flow directly between peers whenever possible.

Use relay nodes only when a direct WebRTC connection cannot be established because of NAT/firewall/network restrictions.

The relay must forward encrypted traffic and must not act as a video-processing server.

# 4. Peer Identity

Every peer must have a cryptographic identity.

Generate a libp2p keypair when the application is first installed.

Persist the private key securely so that the peer retains the same identity across application restarts.

The identity should conceptually look like:

```text
Private Key
     │
     ▼
Public Key
     │
     ▼
Peer ID
```

The Peer ID, rather than an IP address, is the stable identity of a device.

IP addresses are temporary network addresses.

For example:

```text
Peer ID:
12D3KooWExamplePeer

Current addresses:

/ip4/192.168.1.20/tcp/4001

Later:

/ip4/10.20.30.40/udp/4001/quic-v1
```

The Peer ID remains the same while the network address changes.

# 5. DHT

Use libp2p Kademlia for decentralized peer discovery.

The application should be able to perform operations such as:

```text
FindPeer(peer_id)
PutRecord(key, value)
GetRecord(key)
```

Understand that the DHT is distributed.

Do NOT implement a centralized database containing:

```text
Peer A → IP address
Peer B → IP address
Peer C → IP address
```

Instead, Kademlia should distribute routing information among peers.

Each peer maintains only part of the routing information.

Implement:

- Bootstrap peers
- Routing table
- Kademlia queries
- Peer discovery
- Provider records where appropriate
- Record expiration/refresh
- Peer address updates

---

# 6. Bootstrap Nodes

Although the application is decentralized, new peers need a way to enter the network.

Implement configurable bootstrap peers.

Example:

```text
/bootstrap/peer-1
/bootstrap/peer-2
/bootstrap/peer-3
```

Bootstrap nodes should primarily help a new peer discover the network.

Do not make them centralized application servers.

The application should continue operating after joining the network even if one bootstrap node disappears.

---

# 7. WebRTC Signaling

Use libp2p as the signaling transport.

Example:

```text
Alice
  │
  │ libp2p
  │
  │ "I want to call Bob"
  ▼
Bob
```

Exchange:

- SDP offer
- SDP answer
- ICE candidates
- Call ID
- Session metadata

Example:

```json
{
  "type": "offer",
  "call_id": "...",
  "sdp": "..."
}
```

Then:

```json
{
  "type": "answer",
  "call_id": "...",
  "sdp": "..."
}
```

And exchange ICE candidates.

After signaling is complete:

```text
libp2p
   │
   │ signaling
   ▼
WebRTC
   │
   │ audio/video
   ▼
Remote Peer
```

The actual media should NOT travel through libp2p.

---

# 8. WebRTC Connection Strategy

Use ICE for establishing connectivity.

Support:

```text
Host candidates
        ↓
Server-reflexive candidates
        ↓
TURN/relay candidates
```

Use STUN for discovering public-facing addresses.

Use TURN or libp2p relay infrastructure when direct peer-to-peer connectivity is impossible.

The preferred path is:

```text
Peer A ─────────────── Peer B
       Direct WebRTC
```

Fallback:

```text
Peer A ─── Relay ─── Peer B
```

The relay must not decode or process the media.

# 9. Browser Architecture

The browser should use:

```text
React
  │
  ├── UI
  │
  ├── WebRTC
  │
  └── libp2p/browser networking
```

Where appropriate, use JavaScript/TypeScript libp2p for browser-side networking.

The browser must be able to communicate with the Rust-based peers.

Do not assume that browser JavaScript can open arbitrary TCP connections.

Use browser-compatible transports and WebRTC where necessary.

# 10. Android Architecture

For Android, use:

```text
Android UI
    │
    │
Kotlin / Flutter
    │
    ▼
Rust networking core
    │
    ├── libp2p
    ├── Kademlia
    ├── Noise
    ├── Peer identity
    └── signaling
```

The Rust networking layer should be exposed to Android through a well-defined FFI boundary.

Keep the networking implementation independent from the UI.

Possible approaches:

- UniFFI
- JNI
- Rust library exposed through an Android native module

Prefer UniFFI if it provides a clean API for the chosen architecture.

# 11. Important Mobile Networking Considerations

Android devices will frequently change:

```text
Wi-Fi
   ↓
Cellular
   ↓
Different Wi-Fi
   ↓
VPN
```

Therefore:

**Never use the IP address as the identity of a peer.**

The Peer ID must remain stable.

When network connectivity changes:

1. Detect connectivity change.
2. Restart/reconfigure transports if necessary.
3. Discover current addresses.
4. Advertise the new reachable addresses.
5. Refresh DHT information.
6. Reconnect to important peers.
7. Re-establish WebRTC ICE connectivity when required.


Use strongly typed Rust structures internally.

Prefer CBOR, protobuf, or another compact binary serialization for production instead of JSON.

# 13. Security

Security is extremely important.

Use:

- libp2p Noise
- Cryptographic peer identities
- Secure key storage
- WebRTC DTLS-SRTP
- Authentication of signaling messages
- Replay protection where appropriate
- Input validation
- Rate limiting
- Connection limits
- DHT abuse protection

Never trust:

- Peer IDs
- DHT records
- Signaling messages
- ICE candidates
- User-provided metadata

without validation.

Do not transmit private keys to the frontend.

# 18. Critical Design Rule

Keep these layers separate:

```text
┌─────────────────────────────┐
│        React / Android      │
│             UI              │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│       Application Layer     │
│     Calls / Chat / Users    │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│       libp2p Networking      │
│ Discovery / DHT / Signaling │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│          WebRTC              │
│       Audio / Video          │
└─────────────────────────────┘
```

Do not tightly couple WebRTC to the DHT.

The DHT answers:

> "Where can I find this peer?"

libp2p answers:

> "How can I communicate with this peer?"

WebRTC answers:

> "How can these two devices exchange real-time audio/video?"
